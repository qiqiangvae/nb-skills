# Skill 体检与改造

## 何时不用

- 从零写新 skill，或只改 `AGENTS.md` / `CLAUDE.md` 的写法：用 `writing-for-agents`。
- 只想知道某个 skill 的某条命令怎么用：直接读那个 skill，不必体检。

## 立场

- **只读体检**：审计阶段不改任何文件——不改被审 skill，也不顺手改 README、脚本、格式。所有修法先进改动表。
- **确认后才落刀**：用户明确说"改吧""按这些改""第 2、3 条改掉"才动文件。"继续""嗯""看着办"和继续提问都不算。交完报告问一次，然后停在那里。
- **开工前已授权也算确认**：用户一开始就说"直接改""改完给我看"，报告后可直接落改动表里的形式项；质疑项仍逐条等定。
- **先读全再动刀**：`SKILL.md` 和它引用的每个文件都要读到。只读入口就把分册当冗余删掉，是这类审查最常见的破坏。
- **指不出行就不是发现**。说不清改哪一句的问题，回到文件里再看一遍。
- **删是默认动作**（落刀阶段），改写要从"这句话到底改变哪个动作"里挣回成本。

## 第 1 遍：合理性

先查内容对不对，再查写得好不好——规则本身错了，润色它是白做。逐条找下面七类，每条都要能举出「哪种输入下会出错」；举不出就是偏好，不是漏洞。

- **判据兑现不了**：判据要的证据没有任何步骤采集；用 X 验证 X（"跑通了说明没问题"）。
- **步骤链断开**：上一步的产出不是下一步的输入；某步骤需要的输入全文没要求过；分派表里的分支在流程里没有入口。
- **承诺超出能力**：description 或正文承诺的输出，流程不可能产出（要发布却没有写权限、要"自动"却只有人工步骤）。
- **自相矛盾**：两处规则打架；同一阈值出现两个数字；"从不"后面又"可以"。
- **事实过期或错误**：命令、API、字段、路径、版本号、阈值。能跑就跑，能查就查，不要凭印象判断对错。
- **副作用没闸门**：删除、发布、付费、对外发消息这类不可逆动作没有确认；只写成功路径，没写失败怎么收。
- **覆盖缺口**：声明要处理的分支里，有一个在流程上走不通。

处理：进质疑表，**不落刀**。可以附"我会怎么改"，标明是建议；用户说按建议改时再动，并在改动表标注对应的质疑。

**完成判据**：每条质疑都能举出一种会出错的具体输入或场景；举不出的删掉，不凑数。

## 第 2 遍：脚本

`scripts/` 是 skill 里唯一会真的出错的地方：文字写错只是引导偏差，脚本写错会静默给出错结果。没有 `scripts/` 就跳过本遍。

- **密钥与凭证**：硬编码的 token / key / password / 私钥 / 带密码的连接串；密钥被打到 stdout、写进产物或日志。一律报告，并提醒去轮换——进过 git 历史就算泄露。
- **危险操作**：`rm -rf`、`find -delete`、`git push --force` / `reset --hard` / `clean -fdx`、`git branch -D`、`kubectl delete`、`terraform destroy`、`aws s3 rm --recursive`、`docker rm -f`、`DROP TABLE`、`sudo`、`chmod 777`、`shutdown`、`curl … | sh`、`shell=True` / `os.system`（命令注入面）、不给备份就覆盖已有文件。一律报告。唯一可接受的标准：脚本本身就是执行这个动作的工具（发布技能里的 push），且时机、目标、回滚都写在闸门里。清自建临时目录（`mktemp` / `TemporaryDirectory`）不算。
- **改用户的全局状态**：`git add -A`、`git stash`、`git config --global`、往 `~/.bashrc` 里写——扫描、统计类脚本不该动别人的仓库和配置；要动就先说清并留退路。
- **写死的路径**：`/Users/<人>`、`/home/<人>`、`C:\Users\…`；相对路径按 cwd 解析而不是按脚本所在目录；假定临时目录存在。改法是从脚本自身位置推导，或读环境变量。
- **失败静默**：没有 `set -euo pipefail`、错误被吞、退出码恒 0、只打印不 `exit 1`。这是 skill 脚本最贵的缺陷：它让 agent 相信一个假成功。
- **依赖与工具**：调用的命令没装也不报错；承诺零依赖却 import 了第三方。
- **输出不可用**：只打人读文本，agent 拿不到结构化结果；产物路径没打印，agent 不知道写到哪。
- **文档与实现不符**：文档写的子命令、参数、退出码对不上代码（第 1 遍查承诺说不说得通，这里查代码事实）。
- **没人用的脚本 / 文档提了却不存在**：跑脚本查，不靠眼睛。

能跑就跑，但只在确认只读的前提下：`python3 -m py_compile`、`bash -n`、脚本自带 `--test` 或 `selftest`（用临时目录的那种）；拿不准它会不会写文件，就只做语法检查。

处理：密钥、危险操作、改全局状态和会改变行为的修法进质疑表；语法、路径派生、退出码、缺 shebang 进改动表。危险操作只报不改——删掉一行 `rm -rf` 可能把脚本改成另一种错。

**完成判据**：`scripts/` 下每个文件都过了密钥扫描、危险操作扫描与语法检查；每条脚本质疑都能指出"哪种输入下会悄悄给错结果"，危险操作要指出它删/改的是什么。

## 第 3 遍：触发器

description 的措辞决定可靠性，不是它指向的内容。

- **只有"是什么"没有"什么时候用"**：`把数据做分析` 这类描述没有匹配点。改成用户真会说的句子。
- **同义堆叠**：三个近义词指向同一个分支，等于一个分支写三遍。折叠到最常用那个说法，把位置让给真正缺失的分支。
- **承诺了正文没有的分支**：description 说了场景、正文没有对应流程，是最贵的触发器缺陷。补流程，或删掉那个触发词。
- **没有负向边界**：相邻 skill、相邻任务被误触发时，加一句"何时不用"并指路，比再加三个触发词更能提精度。
- **复述正文已有的身份**：description 重复第一段的自述，白占每轮常驻预算。删。
- **用户级 / 模型级选错**：只可能由人想到 → 设 `disable-model-invocation: true`，省掉常驻 description；要被自动触发或被别的 skill 调用 → 必须留 description。
- **三套词**：用户的说法、description 的触发词、正文的用词互不相同，模型接不上。统一到一个 leading word。

**完成判据**：description 里每个词都能对应正文的一条流程或一个分支；删掉任一个触发词，都能举出一个真实场景会漏触发。

## 第 4 遍：编写过程残渣

- **取舍叙述**：`为什么不用 X`、`对比过三种方案`、`经确认采用`。
- **变更史**：`原方案是…`、`现改为…`、`已废弃`、`上一版`、`v2 起`。
- **协商痕迹**：`按你的要求`、`如你所说`、`我们决定`。
- **未决项**：`TODO`、`待定`、`暂定`、`后续再说`。

处理：删，进改动表——skill 是运行时的指令集，不是决策档案。唯一例外是这个取舍会改变 agent 的动作，那就改写成一条现在时规则（「用 X，用 Y 会导致 Z」）。

**完成判据**：全文搜不到上面四类词；每条规则都是"做什么"，没有一条是"当初为什么选它"。

## 第 5 遍：无关说明

- **环境缓存**：目录树、`--help` 输出、`package.json` 脚本、字段的显而易见含义。删，让 agent 现查。
- **背景与动机**：X 是什么、为什么要有这个能力。删，除非它决定某个分支的判定。
- **邻域教程**：把"不负责的部分"讲成教程。压成一句边界 + 指路。
- **空话**：`尽量`、`注意`、`务必`、`好好做`。换成可判定的条件，或整句删。
- **重复**：同一含义在入口与分册各一份。留一个唯一事实源。

**完成判据**：每句都能回答"在哪个分支上改变哪个动作"；答不出来的都删了。

## 第 6 遍：结构

- **层级**：步骤必须在第一层；只有部分分支才需要的参考下沉到 `references/` 并用指针触发；所有分支都要的留在正文。
- **分派**：入口只做分派 + 公共前置；一册一分支；分派表与文件一一对应。
- **判据缺失或模糊**：步骤没写怎么算做完，或用「理解到位」这类界——它会诱导 agent 提前收工。（判据能不能兑现归第 1 遍）
- **就近**：一个概念的定义、规则、坑放在同一标题下，别散在三处。
- **长度**：入口连续超过约 220 行、或读下来注意力明显变稀，先找该下沉的参考，再考虑拆文件。
- **死链与孤儿**：引用的文件不存在，或存在的分册没人引用。不要用眼睛查，跑脚本。

**完成判据**：入口里没有"只有一条分支才会读"的内容；`python3 scripts/lint_skill.py <skill 目录>` 硬问题为 0。

## 报告（先交这个）

两张表：

- **改动表**：位置 / 类别 / 处理 / 影响到什么。
- **质疑表**：位置 / 质疑 / 会怎么错 / 需要你定。

交完就停，等一句明确的确认。职责边界的变化单独说明；改动表里写明"待确认"。

## 落刀（确认之后）

1. 只改用户确认的条目，删优先。没确认的，连"顺手"的一处也不改；确认范围外面的问题留在表里不执行。
2. 全文重读：剩下的每句都能指到某个触发或某个动作。改到结构就整节重写——不追加"变更说明"、不留删除线、不写 `原方案已废弃`。
3. 跑机械检查：`python3 scripts/lint_skill.py <skill 目录>`（脚本自检用 `--test`）。
4. 回报三件事：确认了几条、实际改了哪些、哪些没动（含没拿到确认的）。

## 机械检查的边界

脚本只判机器能判的：frontmatter 与目录名、死链、孤儿分册、疑似密钥、脚本语法错误、危险操作（递归删除、改写远端或历史、云端销毁、管道执行外部代码、提权、命令注入面），加上超长入口、重复句、指向 skill 之外的链接、写死的个人路径、改用户仓库状态的命令、没人引用的脚本、残渣词与空话的高亮。它只读：不写文件、不执行被测脚本。它对**一个 skill 目录**跑；一个仓库里套了多个 skill 时逐个跑。**提示是线索不是结论**——本文件的四类清单自己就会命中残渣词，那是反例，不是待删内容。合理性不归脚本：脚本跑绿不代表内容没漏洞，质疑表只能由读全文的人写。
