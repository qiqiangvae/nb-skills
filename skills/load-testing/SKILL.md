# 压测

把"我想压测一下"变成**有判定标准、可信度可查、结论可归因**的压测。产出不是数字，是能支撑一个决定的结论；跑出支撑不了任何决定的数字，等于没压。

## 五个钉死的立场

- **判定标准先于脚本**：说不出"什么算不达标"，就不要开跑。
- **先证明压测机不是瓶颈**：最常见的假瓶颈在压测侧。
- **分位数不平均**：总体 p99 由直方图合并得出，不是各次 run 的 p99 求平均。
- **每个结论挂证据**：run 编号 + 指标 + 阈值，缺一不可。
- **说清不能证明什么**：`inconclusive` 是合法结论，比硬凑一个通过/不通过有用。

## 何时不用

- 单接口一次性摸底：直接给一条 `oha` / `wrk` / `k6 run` 命令，不要走访谈。
- 前端性能（LCP/INP/CLS）：那是 Web Vitals 与 Lighthouse 的活。
- 功能测试、接口正确性验证：不是压测。

## 流程

十步。每一步的完成条件写死了，不满足就不要进下一步。第 5 步是安全闸门，跳过它可能把被测服务压垮。

### 1. 收敛问题

**完成条件：一句话写出这次要验证或证伪的假设，并指明它的结论会改变哪个决定。**

说不出决定 → 停下来告诉用户这次压测可能没必要，并说明理由，而不是硬着头皮跑。

把"想看看能扛多少"追问成可证伪的句子，例如"大促流量 5 倍（800 QPS）时，下单链路 p99 ≤ 300ms 且错误率 ≤ 0.1%"。

### 2. 采集

**完成条件：`references/interview.md` 场景卡七个字段全部有值；其中「开工闸门」是用户明确回答，不是 `假设`。**

按 `references/interview.md` 的六轮访谈走——问题、默认假设、答非所问的追问、开工闸门清单、场景卡模板都在那份文件里。能在代码、部署配置、监控里自己查到的（超时设置、连接池大小、实例数、历史 QPS）先查，不要拿去问用户。

用户答不出时给默认假设，记入场景卡并标注 `假设`，最后请用户确认一次。

### 3. 建模

**完成条件：Little's Law 自洽，或明确记录不自洽的原因。**

把业务描述换成流量模型：并发 VU、到达率 RPS、思考时间 think time、请求配比、数据分布。

先定环路类型：**closed loop**（固定并发用户 + think time）模拟真实用户感受，**open loop**（固定到达率、不等响应）测服务端容量与排队。打容量上限用 open loop，模拟真实流量用 closed loop，两者结论不能互换。

交叉验算：closed loop 用 `并发 = RPS × (平均响应时间 + think time)`；open loop 没有 think time，用 `并发 = RPS × 平均响应时间`。设定值与推导值差一个数量级，说明模型错了——先改模型，再写脚本。

### 4. 选形态与工具

**完成条件：写明这次要产出哪条结论，以及不可能产出哪条结论。**

七种负载形态见 `references/load-profiles.md`：smoke / constant / ramp-step / spike / soak / breakpoint / capacity，每种能回答的问题不同。

工具默认 k6（脚本化、CI 友好、结果可判定）；已有 JMX 或团队只认 JMeter 时用 JMeter；一次性摸底用 oha / wrk。

### 5. 定上限与熔断（安全闸门）

**完成条件：红线负载、中止条件、爆炸半径、入口放行、停止机制、恢复方式六项都有用户的明确回答，并留下记录。**

压测能打垮被测服务，这一步是防止这件事的唯一闸门。六项的定义、问法与建议见 `references/interview.md` 的「开工闸门」。**这六项不接受默认值**：用户答不上来就不进入执行，宁可这次压测不做。

用户说不出安全上限时，取"目标负载"与"安全上限"中较小的那个；仍说不出，按目标负载的 1.5–2 倍设台阶，绝不一次跳到理论极限。**先小后大**：从低于目标负载的一档开始，确认服务健康再加档，每档之间留观察窗口。

要跑 breakpoint / stress（压到失效）时，六项全部显式确认，并优先在隔离环境做。

### 6. 预检可信度

**完成条件：`references/metrics.md` 的可信度清单每一项都有结论——通过 / 风险 / 作废并记录。**

压测机 CPU 与网卡水位、压测机是否与被测机分离、数据量与冷热状态、环境隔离、监控是否就位、时钟同步。清单里任何一项都能让这次压测的数字作废；宁可少跑一个 run，也不要跳过预检。

### 7. 脚本实现与校准

**完成条件：校准 run 与手工验证逐条一致（状态码、业务码、结果字段，差异条数 0），且红色校准里脚本把已知失败样例判成了失败。**

AI 写的压测脚本会**静默地错**：跑得很顺，数字全错，这种 run 叫**假绿**。先过静态自检清单（think time、连接复用、参数化数据唯一性、结果字段口径），再跑校准 run：1–5 VU，逐条核对响应码、断言、结果字段。

**红色校准**：断言必须覆盖业务码——HTTP 200 + `code != 0` 是最常见的假绿。拿第 2 步要来的失败样例喂给脚本，它必须被判成失败；断言不会红的脚本，等于没有断言。

**认证先预热**：token 过期与刷新会制造假错误率；并发登录有可能先打垮认证服务，看起来像整体崩了。

**方差先摸清**：对比型压测（跨版本、跨配置）在放量前用同一配置重复 2–3 次，得到 run 间波动区间。没有区间，后面的对比全是噪声。

校准不通过，不许放大负载。

### 8. 执行、观测与收尾

**完成条件：用户拿到能打开的实时看板地址（或记录了替代观测方式）；每个 run 都有元数据和原始数据；收尾清单已执行。**

**实时看板必须交给用户**：工具带实时看板时，把地址、端口、起停方式一起给出来，压测机在远端时说明端口转发方式；看板起不来或环境不允许，就说明替代观测方式（定时快照、日志摘要、周期汇报）。

压测进程作为后台任务跑，不要占住会话，否则无法同时做观测辅助与中止判断。

看板只用于观察稳定性和决定是否中止，不作为判定证据——判定必须回到留存下来的原始数据。

命中第 5 步的中止条件时立即降载或停止，并记录触发时刻与实际压力值——这个时刻本身是重要证据。

元数据：时间、脚本版本、目标版本与配置、数据状态、形态与参数、压测机规格。缺元数据的数字不可复用、也不能跟别的 run 比较。原始结果（直方图 / CSV / JSON）留在磁盘上，截图和平均值不算留存。

**收尾清单**：停掉压测进程（包括自己起的后台任务）、恢复被静音的告警、清理或登记待清理的造数、按第 5 步确认的恢复方式回滚、把环境交还。跑完直接进判读、不收尾，等于把事故留给下一个人。

### 9. 判读与归因

**完成条件：每条结论都能指向 run + 指标 + 阈值，标注证据等级（观测 / 推断 / 未知）；跨版本比较里每条"改进"都超过 run 间方差。**

判读按 `references/metrics.md` 的判读方法走：先看方差，再找饱和点与拐点，交叉验算客户端与服务端口径，最后只写被支撑的部分。

用户问"为什么慢"时，先排除压测机饱和、数据冷热、环境干扰，再往代码层走。

### 10. 输出

**完成条件：报告包含判定、每条结论的证据、趋势图、剩余未知、下一步。**

形状、四张必出的趋势图与文件命名见 `references/output.md`。判定只有三档：`pass` / `fail` / `inconclusive`；`inconclusive` 必须写清缺哪一条证据。

方案与报告落在被测项目的文档目录（没有约定时用 `docs/loadtest/<系统>-<场景>/`），原始数据进同目录 `raw/`，跟着代码一起提交——留在个人下载目录或聊天里的数字，下次没人能复用。
