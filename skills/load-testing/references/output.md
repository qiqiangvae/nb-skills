# 产物契约

压测产物有两个：执行前的**方案**（要被用户确认）和执行后的**报告**（要能支撑决定）。形状固定，字段不可省。

## 方案（执行前给用户确认）

- **目标假设**：一句话，可被证伪；附"它会改变什么决定"
- **判定标准**：延迟分位与阈值、错误率上限、资源红线、不达标时的业务语义
- **开工闸门**：`interview.md` 开工闸门逐项的答案与用户确认记录（缺任一项不许开跑）
- **流量模型**：open loop（到达率）还是 closed loop（并发 + think time）、并发或到达率数值、请求配比、数据规模，含按 `SKILL.md` 第 3 步公式的验算过程
- **执行序列**：形态 + 参数 + 时长 + 终止条件（什么情况提前中止）
- **环境与预检**：可信度清单逐项结论
- **工具与脚本**：选型理由、校准计划、脚本自检结果
- **风险与不能证明的部分**：显式列出

用户没确认方案就不要开跑。

## 报告（执行后输出）

- **判定**：`pass` / `fail` / `inconclusive`；`inconclusive` 必须写明缺哪一条证据
- **结论清单**：每条 = 结论 + run 编号 + 指标值 + 阈值 + 证据等级（观测/推断/未知）
- **瓶颈链**：首个饱和资源 → 次生瓶颈，附对应数据；含下游与第三方是否被牵连
- **方差**：各关键指标的 run 间波动区间，以及哪些结论超过了方差、哪些只是噪声
- **趋势图**（见下节，缺图视为报告未完成）
- **剩余未知与风险**
- **下一步建议**：扩容、优化、还是补测哪一项

没有"下一步"的报告等于只交了一半。

## 趋势图

报告必须能"一眼看出趋势"。图的 X 轴优先是被控变量（并发或到达率），时间轴图只作为稳定性证据的补充——单次 run 的时间序列看不出容量。

必出四张：

- **吞吐-并发折线**：标出拐点（RPS 不再线性增长的位置）
- **延迟-并发折线**：p50 / p95 / p99 同图三条，标出 p99 开始指数上翘的位置
- **错误率-并发折线**：区分超时、5xx、断言失败，不合并成一条"错误率"
- **资源水位-时间折线**：CPU、内存、连接池占用；有多台实例时画分布而不是均值

按需追加：

- **多版本 / 多 run 对比分组柱状**：同一负载下的 p99、吞吐、错误率并排
- **客户端与服务端同轴叠加**：把服务端 CPU 或连接池等待与客户端 RPS 画在同一时间轴，用来做因果归因
- **延迟分布直方图**：看长尾形状，比单个分位数更能说明问题

画图的两条硬约束：

- 每张图标注数据来源的 run 编号，图与 `raw/` 里的原始数据必须对得上
- 图是结论的证据，不是装饰：结论里引用的每个拐点都要能在图上指出来

格式优先 HTML 或 SVG（可交互、可放大），其次是 PNG；不要用终端字符画当报告交付物。

## 文件命名

默认落在被测项目的 `docs/loadtest/<系统>-<场景>/`：

- 方案：`loadtest-<系统>-<场景>-<日期>-plan.md`
- 报告：`loadtest-<系统>-<场景>-<日期>-report.md`
- 原始数据放同目录 `raw/`，报告里引用文件名，不要内联贴大段数据
