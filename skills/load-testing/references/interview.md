# 采集访谈

## 原则

- **先查再问**：代码里的超时/连接池/重试配置、部署拓扑、监控面板、历史 QPS，能自己查的一律不问用户。
- **一轮 ≤4 问**：先开放式问，再用选项收敛。问太多等于逼用户编答案。
- **能用选项就用选项**：宿主有多选题、确认卡这类交互就调它，没有就用编号列表；每问带上默认值，以及"不知道"时怎么办。
- **答不出就给默认值**：给一个行业经验默认值，标注 `假设`，最后统一确认。不要让访谈卡死。
- **每轮复述**：用 3–5 行复述已确认内容，让用户当场纠正，而不是最后返工。

## 第 0 问（开放式，必问）

> 这次压测你想解决什么问题？它的结论会改变什么决定？

压测要花掉环境、时间与风险成本，没有决定的压测应当被劝退。答不出时，直接把候选决定列出来让用户勾：上线放量 / 扩容决策 / 架构改造 / 定 SLO / 排查已知慢点。

## 第一轮：被测系统

- 入口与协议：域名与接口清单，HTTP、gRPC 还是 WebSocket
- 关键链路：只读浏览、搜索、下单、支付——这次压哪一条，还是按比例混合
- 部署形态：几台什么规格、前面有没有网关/负载均衡、依赖哪些中间件（DB、缓存、消息队列）
- 有状态部分：登录态、写库、幂等键、分布式锁、限购
- 服务端监控能不能拿到：CPU、内存、GC、连接池、慢查询、中间件指标

默认假设（用户不知道时）：预发环境、单链路、能拿到基础监控。

## 第二轮：流量模型

- 当前真实流量：峰值 RPS/QPS、并发用户数、时间分布（工作日/大促/有无尖峰）
- 目标：倍率（2x / 5x / 10x）还是绝对目标
- 用户行为配比：浏览 : 搜索 : 下单 = ?
- 数据规模：用户数、商品数、热点分布、参数化数据集大小
- 思考时间：真实用户两次操作之间隔多久

默认假设：恒定负载、配比按用户指出的主链路全打、think time 取 1–3 秒。

## 第三轮：判定标准（不可跳过）

- 延迟：p95 / p99 的上限，以及统计的是 TTFB 还是完整响应
- 错误率上限，以及 4xx 算不算错
- 资源水位红线：CPU、内存、连接池到多少算不可接受
- 业务语义：不达标意味着什么（降级？不能上线？必须扩容？）

用户说不出阈值时，给 2–3 个候选区间让他选，不要替他静默决定。默认假设：p95 ≤ 500ms、错误率 ≤ 0.1%、CPU ≤ 70%——给出来时必须标注为假设并要求用户确认。

## 第四轮：安全边界（不可跳过）

压测能打垮被测服务。这一轮逐条问「开工闸门」里的六项安全边界，**不接受默认值**：用户必须明确回答，答不上来就不进入执行，宁可这次压测不做。

要跑 breakpoint / stress（压到失效）时，把"这可能把环境打挂"讲清楚，优先换隔离环境，六项都要用户显式点头。

## 第五轮：约束

- 环境：能不能用生产？能不能污染数据？有没有影子库/脱敏数据
- 时间窗：能占用多久，会不会影响同环境其他人
- 压测资源：几台机器、带宽多少、是否与目标同网络区域
- 是否需要分布式（单机打不上去时）

默认假设：预发环境、可清库、压测机 1 台。

## 第六轮：已有资产

- 已有脚本（JMX / k6 / 其他）、历史压测结论、SLO 文档
- CI/CD 里有没有性能门禁
- 已知教训：上次压测踩过什么坑

## 开工闸门

访谈到这里，下面每一条都要有明确答案才能开工——写脚本之前问，跑起来之后再问就晚了。**全部不接受默认值**，答不上来就把压测停在这一步。

### 安全边界

1. **红线负载**：允许的最高并发或到达率，超过多少绝对不能再加。用户说不出安全上限时，按目标负载的 1.5–2 倍设台阶，一次只加一档，让他确认这一档可以打。
2. **中止条件**：什么情况必须立刻停——错误率、p99、5xx 激增、CPU、下游开始报错、用户打电话喊停。
3. **爆炸半径**：打垮了会怎样、波及谁。会不会写脏数据、是否与生产流量共用、影响哪些业务、谁批准了这次压测。**必须把下游与第三方算进半径**：DB、缓存、MQ、合作方 API 是否会被打到、有没有配额或按量计费、会不会被对方限流。
4. **入口放行**：压测机 IP 加白了吗，风控关了吗，网关、CDN、限流规则会不会先拦掉压测流量。没确认就开跑，测到的是 WAF 的阈值，不是自己的容量。
5. **停止机制**：谁有权喊停、怎么停（kill 进程 / 看板降载 / 脚本停止）、由 agent 执行时允许它直接中止吗、停不下来时怎么兜底。
6. **恢复方式**：数据能否回滚、缓存与消息积压怎么清、要不要重启、恢复要多久。

### 数据可信

7. **业务码口径**：接口怎么算成功？HTTP 200 里的 `code` 会不会非 0？业务失败算不算进错误率？要一份成功样例和一份失败样例——失败样例是红色校准的输入。
8. **认证与 token**：用什么认证、多久过期、要不要刷新、要不要在压测前批量预热，登录服务能不能扛住并发登录。
9. **数据准备与清理**：谁造数（规模、唯一性、热点、脱敏）、跑完谁清、能不能清库、要不要回滚。
10. **压测流量识别**：请求能不能打标，监控与告警能不能排除压测流量或临时静音，要不要写影子表，谁盯屏。
11. **重复与方差**：同一配置允许跑几次；版本对比以"差值超过 run 间方差"为改进门槛，能接受吗。

任何一项含糊，都会在压测中变成假数据或事故。

## 答非所问时的追问

- "就想看看能扛多少" → 追问"扛多少用来做什么决定"。仍无决定 → 改为 capacity 摸底（画吞吐-并发曲线），并明确它不产出通过/不通过。
- "随便压一下" → 提醒这要花掉一次环境窗口；给最小可行方案：smoke + 一个稳态点。
- "和上次一样" → 要上次的 run 元数据。没有元数据就不能直接比较，只能重跑基线。
- "要 10 万 QPS" → 先反推可行性：10 万 QPS × 平均响应 100ms ≈ 1 万并发；问压测机与带宽是否支持，不支持则拆分目标或改分布式。
- "用 JMeter 压" → 工具不是目标，先确认要产出的结论，再决定工具。

## 场景卡模板

访谈结束输出这张卡，七字段缺一不可：

- **目标假设**：一句话，可被证伪；附带它会改变的那个决定
- **被测系统与链路**：环境、入口、协议、依赖、监控可用性
- **流量模型**：环路类型、并发或到达率、think time、请求配比、数据规模，含 Little's Law 验算
- **判定标准**：延迟分位与阈值、错误率上限、资源红线、业务语义
- **开工闸门**：安全边界六项 + 数据可信五项逐条有明确答案，不允许标为 `假设`
- **约束条件**：环境可用性、时间窗、压测资源、是否分布式
- **已有资产**：脚本、历史结论、门禁、已知教训

除「开工闸门」外，其余字段里的 `假设` 单独列一段，请用户逐条确认或修改。
